# プロジェクト概要

コブチョウ ミニ版（kobutsu-ledger-sample）— 副業・個人の古物商向けの台帳アプリ「コブチョウ」を、**設計と開発規約を見せるために機能を絞って公開した版**。
Repository パターン + Service レイヤー（Laravel）+ Inertia + React の構成（Laravel 公式 React スターターキットの構成に準拠）。

## このリポジトリの目的

- 実際のサービスと同じ構成・同じ規約で書いたコードを、公開できる範囲に絞って示す。
- 残しているのは中核の「**仕入・売却を記録すると、古物営業法で義務づけられた古物台帳（施行規則 別記様式第15号）ができあがる**」部分。
- 規約は人と AI エージェントの両方が読む前提で書いている。入口は リポジトリ直下の `AGENTS.md`。

## 規約（`docs/conventions/`）の位置づけ

- 本ディレクトリは **どう作るか（How・コーディング規約）** を担当する。何を作るか（What）は本ファイルの「できること」と、コード・テストが正。
- 規約のうち機械で線を引けるものはツールで確かめる（本文の 🤖 印。どの規約を何で確かめているかは [90-review-checklist.md](90-review-checklist.md) の表が正）。
- 規約に書いていないこと（命名・画面とサーバーの境界の細部など）は、既存のコードの書き方に合わせる。

## 技術スタック

- PHP 8.3 以上（Laravel 13 の必須要件）
- Laravel 13（Inertia 3 で画面に props を渡す）
- React 19 + TypeScript（strict）+ Tailwind CSS 4（Inertia 3 のページ。React Compiler 有効）
- Wayfinder（ルートの TS 生成）/ shadcn/ui（Radix）/ Heroicons / sonner（トースト）/ Vite+（ビルド・Lint・整形。Node 22.12 以上）
- 認証は Laravel 標準のセッション（web ガード）。SSR は使わない
- PDF: mpdf（様式15号の帳票）
- DB: 既定は SQLite（`.env.example`）。Laravel Sail（`compose.yaml`）で MySQL 8.4 も使える
- テスト: PHPUnit + Laravel Feature テスト（`RefreshDatabase`・`assertInertia`。メモリ上の SQLite）+ Playwright E2E
- 静的解析: PHPStan + Larastan（自作ルール付き）/ PHP_CodeSniffer（自作ルール付き）/ ESLint（命名だけ）/ Oxlint・Oxfmt・tsc

## できること（このリポジトリの範囲）

- **認証**：ログイン・新規登録・ログアウト（ログインと登録にはレート制限）。設定画面で氏名と、帳票に刷る営業所名・古物商許可番号を変更する
- **仕入（受入）**：在庫の一覧・検索・状態（在庫中 / 売却済 / 下書き）の絞り込み・登録・更新・論理削除。現場では写真と金額だけで下書き保存し、あとで完成させられる。相手方は過去の仕入から候補を出す
- **仕入の写真**：1つの仕入につき5枚まで。実体は Web 非公開の local ディスクに置き、本人だけが認証付きのルート `/photos/{id}` で取得できる（他人は URL を知っていても 404）
- **売却（払出）**：1仕入＝1売却。売却を記録すると在庫から外れ、台帳に払出の行が立つ。売却を取り消すと在庫に戻る
- **古物台帳**：受入と払出の時系列1表。台帳は保存せず、仕入・売却の記録から都度組み立てる。期間と検索語で絞り込める
- **様式15号の出力**：PDF（mpdf・A4横・ブラウザで即表示して印刷できる inline）と CSV（Excel で文字化けしない UTF-8 BOM 付き）

## このリポジトリに含めないもの

元のサービスにある次の機能は外している（コードにも規約にも無い）。

- 課金（Stripe）と有料プラン、損益レポート・確定申告用の CSV
- 管理画面・管理者アカウント・代理ログイン
- お問い合わせ、メール送信（パスワード再設定を含む）
- 本番環境へのデプロイ

## ドメインの要

- **purchases（仕入＝受入）が台帳の核**。sales（売却＝払出）は **1仕入＝1売却**（ロット分割はしない）
- **状態（在庫中 / 売却済 / 下書き）はカラムを持たない**。`sale` の有無と `is_draft` から導出する
- **相手方はマスタ表を作らない**。`purchases` から DISTINCT で候補（チップ）を出す
- **下書き（`is_draft`）**：DB は nullable にし、確定時の必須項目チェックはアプリ層（FormRequest）で行う
- **論理削除のみ**（台帳は法定3年保存。物理削除しない）。例外は写真（法定の記載事項ではないので、消したら行もファイルも消す）
- 固定のステータス・種別は **PHP Enum**（3個）で管理し、DB マスター化しない：`Kubun`（受入れの区別＝買受け / 委託）/ `VerificationMethod`（相手方の確認方法）/ `SalesChannel`（販路）
- スコープの外：一般経費は扱わない（売却に紐づく手数料・送料だけ）／相手方の本人確認はガイドの表示まで（アプリで確認を強制しない）

## ドメイン分類

`Auth`, `Purchase`（写真の `PurchasePhoto` を含む）, `Sale`, `Ledger`
