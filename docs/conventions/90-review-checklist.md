## 機械で確かめる規約（CI と push 前のフック）

規約のうち、機械で線を引けるものはツールで確かめる（本文の 🤖 印）。**CI（GitHub Actions）で push とプルリクエストのたびに流す**（test ジョブ＝下の表の E2E 以外、e2e ジョブ＝Playwright）。push 前のフック（`.githooks/pre-push`）でも、E2E を除いて同じものが流れる。

| 規約 | 道具 | コマンド |
|---|---|---|
| 書き方の整形・一般的なバグのもと・型（TS） | Oxfmt・Oxlint・tsc | `npm run check` / `npm run types:check` |
| 配列は `xxxList`・自分の関数に `on*` / `handle*` を付けない・型の名前は PascalCase で `Data` で終わらない・ファイル直下の定数は大文字（09） | ESLint（typescript-eslint の naming-convention。`eslint.config.ts`） | `npm run lint:naming` |
| PHP の型の食い違い（既存の指摘は `phpstan-baseline.neon` に記録して受け入れ、新しいコードから厳しく見る） | PHPStan + Larastan（レベル5。`phpstan.neon`） | `composer phpstan` |
| 配列の値に条件式を書かない（03）・Repository で `count()` から `first()` を呼び直さない（07） | PHPStan の自作ルール（`tests/PHPStan/Rules/`） | `composer phpstan` |
| `fn()`（空白なし）・キャストのあとに空白を入れない・メソッドのあいだは3行（03） | PHP_CodeSniffer と自作ルール（`phpcs.xml`・`phpcs/Kobucho/`） | `composer phpcs` |
| サーバーの動き・画面の動き | PHPUnit・Playwright（E2E は CI の e2e ジョブ。フックには入れない） | `php artisan test` / `npm run e2e` |

- 自作ルールの違反は `phpstan-baseline.neon` に入れず、コードを直す（ベースラインの作り直しは `composer phpstan:baseline`）。
- PHPCS の指摘は `vendor/bin/phpcbf` で自動修正できる。PHP の整形に Pint は使わない（手書きの規約が正。デフォルトのプリセットは規約と合わない）。

## レビューで確かめる規約（機械では線を引けないもの）

- オブジェクトの変数は `xxxData`（ライブラリの `form`・`page`、画面の状態の `saleForm` など例外が多く、機械では線を引けない）
- 関数名は動詞から始める・値の名前は名詞だけにしない（`record_type`）
- if は肯定文で書き、else で NG を受ける・JSX の外で三項演算子を使わない
- 層の役割（Controller / Service / Repository）・ログの残し方・docblock の書き方

## 命名 (Ch.11)

### 良い名前の条件
- 変数が表すものを完全かつ正確に説明しているか。
- プログラミング言語の解決策ではなく、現実世界の問題を表しているか。
- 意味を解読する必要がないほど十分に長いか。
- 計算値を修飾子として使用する場合は、名前の末尾に追加しているか。

### 特殊なデータの命名
- ループ変数: 3行以上のループやネストしたループでは、`$i` ではなく意味のある名前を使う。
- 「一時」変数を意味のある名前に変更したか。
- ブール変数: true の場合に意味が明確になる名前か（例: `$isValid`, `$hasPermission`）。
- 定数: 数値ではなく、表す意味に由来する名前か。

### 避けるべき名前
- 誤解を招きやすい名前 / 似通った意味を持つ複数の名前
- 1、2文字異なるだけの名前 / 同じような発音の名前
- 短くするために意図的に綴りを変えた名前
- 標準ライブラリや既定の変数名と競合する名前

## データ型 (Ch.12-13)

- マジックナンバー・マジックストリングを使っていないか。定数クラス（Consts）を使う。
- 「0による除算」エラーが起きる可能性はないか。
- 型の変換は明白か。同じ式に異なる型の変数を混在させていないか。
- 整数の除算・桁あふれは正しく処理されているか。
- 浮動小数点数の等価比較をしていないか。丸め誤差を防いでいるか。
- ブール変数を追加して、複雑な条件の評価を単純にできないか。
- 配列のインデックスが有効範囲内にあるか。「1つ違い」エラーはないか。
- 関連するデータをクラスにまとめることを検討したか。
- すべての変数をローカル変数またはクラススコープで宣言しているか。

---

## コードの構成 (Ch.14)

- ステートメントどうしの依存性が明白になるように書かれているか。
- コードは上から下へ読めるか。
- 関連するステートメントを1つにまとめているか。
- 密な依存関係にあるステートメントをメソッドとして独立させているか。

---

## 条件文 (Ch.15)

- 正常なケースの実行パスは明白になっているか。
- else句が明記され、文書化されているか（何もしない場合は「// no action.」）。
- 正常なケースはelse句ではなくif句に続いて処理されているか。
- 複雑な評価をブール変数やメソッドでカプセル化しているか。
- 最も出現頻度の高いケースを最初に評価しているか。
- すべてのケースをカバーしているか。

---

## ループ (Ch.16)

- ループでただ1つの機能を実行しているか。
- ループは全体を一度に参照できるくらい短いか。
- ループのネストは3段階以下になっているか。長い場合はメソッドとして独立させているか。
- forループの内部でループ変数を書き換えていないか。
- ループ変数をループの外側で使用していないか。
- ループはどのような状況下でも終了するか。終了条件は明確か。

---

## return文 (Ch.17)

- 各メソッドは必要なときだけreturn文を使用しているか。
- return文によってコードが読みやすくなっているか。

---

## 制御構造の問題 (Ch.19)

- 論理式に1と0ではなくtrueとfalseを使っているか。
- ブール式は肯定的に表現しているか。
- 新しいブール変数を追加したり、ブール関数やデシジョンテーブルを使用したりして、式を単純にしているか。
- 数値は評価値と明示的に比較しているか。
- 論理式に完全にかっこを付けているか。
- 評価は数直線の順番に書かれているか。
- コードを明確にする必要があるすべての場所に、中かっこ `{}` を使っているか。
- null文は明確に使われているか。
- 深くネストしたステートメントは、条件の再評価・if-then-else/case文への書き換え・メソッドとして独立させるなどで単純化しているか。
- メソッドの判定ポイントが10個を超える場合、再設計しない十分な理由があるか。
